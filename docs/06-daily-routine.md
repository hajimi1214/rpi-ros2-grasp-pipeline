# 开工 / 收工固定流程

每次干活都走这五步，总共 3 分钟。多开对话、多设备改同一个仓库时，这套流程是防止互相覆盖的唯一保障。

---

## 开工三步（1 分钟）

**1. `git pull`**

先同步再动手。你可能会同时开几个对话、或用不同设备改同一个仓库——不同步就开工，写的东西会跟别人的版本打架，最后要么丢失要么手动合并。**这一步不能省，也不能凭记忆觉得"应该没变过"。**

**2. 读 README 顶部那句「本周目标」**

开工前先确认今天要往哪个方向使劲。没有这一句，很容易变成"今天随便搞点什么"，几周后回头发现做的事跟目标没关系。

**3. 今天只做跟这句相关的事**

如果 README 顶部还没写目标（新的一周刚开始），先花 5 分钟写一句再开工。一周只写一个，写两个等于没写。

---

## 收工两步（2 分钟）

**4. `git add -A && git commit -m "..."`**

**哪怕今天只改了一行文档也要提交。** 提交历史本身就是证据链——面试官看仓库时，连续几十天的提交和"一次性传上去"是完全不同的两种观感。

**5. `git push`**

本地提交不等于有证据。仓库是 Public 的，只有推上去才对外可见。

---

## 为什么必须是这五步

| 步骤 | 不做会怎样 |
|------|-----------|
| 开工 pull | 多会话/多设备互相覆盖，改动丢失 |
| 读本周目标 | 时间花了，方向跑偏 |
| 只做相关的事 | 同样是一小时，产出差几倍 |
| 每天提交 | 攒到最后一次性传 → 看起来像抄的 |
| push | 东西只在自己电脑上，等于没有 |

---

## 每周两个固定动作

- **周一（5 分钟）**：写一句本周目标，放到 README 顶部
- **周日（10 分钟）**：填 `02-weekly-log.md`，按「现象 → 根因 → 解法」记这周的坑；对照 `01-metrics.md` 看数字有没有变化

---

## 一条纪律

**卡住超过两天，必须求助**（社区发帖 / 问人 / 换方案），不许硬扛。

参考 `04-info-sources.md` 里的社区清单。硬扛三天的成本 ≈ 别人一句话的收益。
