这一讲里有一段命令演示，是 r2net 的立命之本，务必亲手敲一遍：

```
ros2 topic pub /chatter std_msgs/msg/Int32 "data: 42" --qos-reliability best_effort
ros2 topic echo /chatter --qos-reliability reliable      # 收不到
ros2 topic echo /chatter --qos-reliability best_effort   # 收到了
```

**`topic list` 看得到但 `echo` 收不到，全程无报错。** 这就是 r2net 要解决的症状。

## 三、阶段 2：故障注入周（r2net 的素材来源）

按 `08-multihost-drill.md` 的 10 种故障逐个注入，每踩一个记一条：

```
现象：<原样粘贴终端输出>
根因：<哪一层、哪个变量>
解法：<能直接复制的命令>
```

**这一周你不是在"学习"，你是在给 r2net 攒规则库。** 每记一条，工具就多一条诊断能力。

同时补学（用到什么学什么，不提前学）：

| 概念 | 为什么必须懂 | 学到什么程度 |
|---|---|---|
| **Domain 与端口映射** | domain id 怎么算成 UDP 端口，为什么不同 ID 就互相看不见 | 能算出 `ROS_DOMAIN_ID=5` 对应哪个端口段 |
| **SPDP / EDP 发现机制** | 为什么多播被拦就发现不了；Discovery Server 是什么 | 能讲清"节点怎么找到彼此" |
| **QoS 兼容性规则** | RELIABLE/BEST_EFFORT 谁跟谁不兼容 | 看一眼两端 QoS 就知道通不通 |
| **RMW 差异** | Fast DDS 和 Cyclone DDS 行为不同 | 知道混用会出什么怪现象 |

## 七、多对话怎么分工（重要，你已经开了不止一个）

同时开多个对话改同一个仓库，代价是上下文断裂 + git 冲突 + 重复劳动。
**规则如下，照做不会乱：**

| 规则 | 内容 |
|---|---|
| 1 | **一个对话只负责一件事。** 别让两个对话同时规划同一个问题 |
| 2 | 新对话开场：**先粘启动词**（`new-chat-context.md`），再让它 `git pull` 并读 `docs/07` 和 `docs/08` |
| 3 | **动手前 pull，收工前 push。** 这是唯一防冲突的手段 |
| 4 | **决策只在一个对话里做。** 另一个对话如果发现矛盾，回来问，不要自己改方向 |
| 5 | 决策结果**必须落进仓库**（docs 文件），不能只存在对话里——对话会丢，仓库不会 |

建议分工：
- **本对话**：方向决策、调研查证、文档产出
- **另一个对话**：装机实操、终端报错排查、按既定方案执行

第 5 条最关键：**任何拍板的事，当天写进 docs。** 否则换一个对话就失忆了。
